## 内存占用（`mem` 模式，2026-11-15）

`dotnet run -c Release --project benchmarks/SimdImaging.Comparison -- mem 3840x2160`：**先预热一次**，再连续跑 5 次，
报「峰值增量 / 调用后常驻 / 每次分配」。

| 算子（4K） | 每次分配 | 调用后常驻 |
|---|---|---|
| resize-bicubic / gaussian-blur | 0 | 0 |
| **seam-50** | **39.7 MiB**（原 47.6，`_blocked` 改惰性） | 0 |
| guided-filter / guided.cross | 10.6 MiB | 0 |
| quantize-64 | 1.8 MiB | 0 |
| oilpaint | 1.5 MiB | 0 |

**结论一：不涨。** 除第一支之外，重复调用后 `GC.GetTotalMemory(forceFullCollection)` 相对基线为 0，
说明 `FloatScratch` 与 `ArrayPixelPool` 的保留是有限的、不是泄漏。

**结论二：seam 的 39.7 MiB 里约 33 MiB 是 luma 平面**——那是当天为 −17% 加的（每条缝只算一次 luma，
而不是 50 次）。换来的时间是真的，代价是这个平面本身。**下一个该改的正是它**：8/16 位下 luma 恒为 0..255 的整数，
用 `byte[]` 存放即 4 倍缩减到 8.3 MiB，DP 读入时再展开成 float，字节不变。

**插曲（值得记）**：把插入路径专用的 `_blocked` 掩码改成惰性分配后，**峰值 RSS 一点没动**（8K 仍 416 MiB），
因为 33 MiB 是 LOH 大对象、释放后页仍被进程留着；只有分配口径（这张表）能看到它从 47.6 降到 39.7 MiB。
**两个口径回答的是两个问题**，不能互相替代。

**这个模式测不了峰值**：冷进程试过，七项全读 0 MiB——夹具已经把堆提交好了，17 MiB 的平面落在已驻留页里，
工作集不再增长。绝对峰值仍以 `peakmem`（真子进程）为准。



## Seam Carving 分段剖析（`seamprofile`，2026-11-15）

```
dotnet run -c Release --project benchmarks/SimdImaging.Comparison -- seamprofile
```

相位读数来自**产品算子自己**的 `SeamCarving.ProfilePhases` 计数器（每阶段一次、每缝四次，默认关、
关闭时只剩一个不跳转的分支），不是复刻件的计时——铁律 4 在这里同样适用。每格是**全新子进程**：
三遍 GC 取基线、1 ms 采样 `WorkingSet64`，冷格只调一次、热格 3 次中位。

| 尺寸 | 冷启动总 ms | FindSeam | CutSeam | ShiftLuma | Copy+Prime+Crop | ms/缝 | 峰值 RSS | 调用后 live |
|---|---|---|---|---|---|---|---|---|
| 1920×1080，50 缝 | 456.7 | **374.2（82%）** | 26.6（5.8%） | 24.0（5.3%） | 28.9（6.3%） | 9.1 | 28.4 MiB | 16.0 MiB |
| 3840×2160，50 缝 | 1722.9 | **1455.4（84%）** | 101.6（5.9%） | 102.9（6.0%） | 60.3（3.5%） | 34.5 | 107.5 MiB | 64.0 MiB |
| 7680×4320，10 缝 | 1526.9 | **1196.0（78%）** | 73.3（4.8%） | 73.8（4.8%） | 180.9（11.8%） | 152.7 | **416.3 MiB** | 254.0 MiB |

两条自检列是这张表存在的条件：**Σ相位/总 = 99.7–99.9%**（漏了括号点就会掉下来），
**同尺寸冷热 SHA 相同**（不同尺寸的 SHA 本来就不同，拿它们互比是错的——第一版就是这么错的）。

**2026-11-16 更新**：整数 DP（8 lane）后 FindSeam 占比从 82% 降到 72%，总时长 1080p 457 → 277 ms；
luma 改 `ushort` 后 8K 峰值 RSS 从 415 降到 **352 MiB**（正好是 luma 减半），`ShiftLuma` 从 25.4 降到 15.6 ms。

结论：**85% 的时间在 `FindSeam`**，Cut/Shift 各 5%。所以「减少数据搬移」（Cut/Shift）天花板是 10%，
真正的空间在能量与 DP 内部。内存侧 8K 峰值 416 MiB 里，`Workspace` 推算约 199 MiB（其中 `_blocked`
33 MiB 在删除路径上从不被读）。


### 能量在 `FindSeam` 里只占 17%（消融，2026-11-16）

`FindSeam` 占整次切割的 80–85%，所以「增量能量更新」看着像大机会。**消融说不是**：把 `Energy()`
在标量路径与 `WriteRow4` 里同时短路（只测时间，字节必然变，用完即回滚），1080p 删 50 列：

| | FindSeam | 总时长 |
|---|---|---|
| 原样 | 400.5 ms | 487.2 ms |
| 能量短路 | **331.4 ms** | 447.6 ms |

**能量 = 69 ms = `FindSeam` 的 17%、总时长的 14%。** 即使缓存命中率 100% 也只值这么多，而增量实现
还要为「逻辑列 → 原始列」付 gather 的代价。结论：瓶颈是 **DP 递推本身**，那条 O(W·H) 且已向量化的链。
这条实验同时说明 `known-gaps.md` 里原来的否决理由（「受影响列无上界」）**不成立**——按原始坐标存时每行只
变 1–2 格；结论仍然是不做，但依据换成了这个数字。


### seam 的 8K 内存账（2026-11-16）

峰值 **352 MiB** 的构成，以及每一块能不能动：

| 块 | 8K 字节 | 能不能省 |
|---|---|---|
| 源图副本（`Transforms.Copy` 进工作缓冲） | 133 MiB | **不能**：carve 就地改像素，不能改调用者的图 |
| `Crop` 的结果缓冲 | 132 MiB | **不能**（见下） |
| Workspace：luma `ushort` | 66 MiB | 已减半（原 float 132） |
| Workspace：`_back` | 33 MiB | 能，但见下 |
| Workspace：行缓冲 / `_seam` | <1 MiB | — |

**为什么 `Crop` 不能省**：`PixelView.Span` 返回的是 `Stride × Height` 字节。如果让结果直接复用工作缓冲、
只把 `Width` 改小，那么每个用 `WritablePixels` / `ToArray()` 的调用者都会读到**被删掉的那些列**（陈旧字节）。
Crop 存在的理由就是这个契约；去掉它等于允许「非紧凑结果」，那是公共 API 的设计变更，不是局部优化。

**为什么 2-bit parent 现在不做**：`_back` 33 MiB → 8 MiB 是真的，但写入点在 DP 内层（占 72% 的时间），
而按 4 格打包会引入跨字节的读改写（`row + x` 从 x=1 起步，不保证 4 对齐）。**用最热的那条循环换 25 MiB**，
在现在的性能曲线上不划算。等有独立需求（比如 16K）再评估。








## 尺寸 × 工作格式矩阵（`matrix` 模式，2026-11-15）

`dotnet run -c Release --project benchmarks/SimdImaging.Comparison -- matrix` 跑三个尺寸 × 两种工作格式，
每格都是一次完整的同进程 A/B（cold + steady 7 轮交错、进程级分配、峰值 WS），尺子与 `perf` / `perf16` 完全相同，
**没有新增度量**。

| 尺寸 | Rgba8（19 项） | Rgba16（7 项） |
|---|---|---|
| 640×360（0.23 MPix） | 1.5050×（领先 13 / 持平 2 / 落后 4，**含一格离群**） | **2.8424×（7/7）** |
| 1920×1080（2.07 MPix） | **2.3403×（19/19）** | **2.7361×（7/7）** |
| 3840×2160（8.29 MPix） | **2.0257×（19/19）** | **2.7433×（7/7）** |
| 7680×4320（33.2 MPix） | **2.0038×（19/19）** | **2.5553×（7/7）** |

> 640×360 那一格的「落后 4」里有一格是**离群值**：该轮 `resize-bicubic` 读到 0.38×（我方 5.32 ms），
> 而 `repeat.sh perf 640x360 3` 复核为 **4.22×（3.98–5.37）**，六轮中位 4.06×。剔除后是**领先 14 / 持平 2 / 落后 1**
> （唯一的真落后是 `pixelate`）。**单次 matrix 运行可能被一个受干扰的单元格带偏整行结论**——这正是 `repeat.sh` 存在的理由。
>
> 第一版矩阵只到 4K，是漏项——8K 那一格才暴露出下一节说的问题。参数档位现在也在每个尺寸上跑
> （质量与尺寸会相互作用：σ=1 的模糊在 1080p 便宜，8K 不便宜）。

**小尺寸不是弱点，是测量地板**：640×360 上 19 项原本报「15/19 领先」，但把逐项拉出来看，落后的几项是
0.95–0.99× 或 0.06–0.21 ms 的**亚毫秒**场景。`resize-nearest`（0.09 vs 0.058 ms）在两次运行之间从 1.46× 摆到
0.64× —— 这个量级的抖动来自测量本身，不是算子。因此判定列改成三档（领先 >1.05× / 持平 / 落后 <0.95×），
报告写成「领先 14 / 持平 3 / 落后 2」而不是「15/19」。**亚毫秒场景不引用为胜负**，要么加大轮次，要么不报。

试过并回滚的：把 `RowParallel` 的固定 64K 像素门槛改成「按工作量给 worker 数」（32K 像素/worker）。
点算子确实变快（brightness 0.90× → 1.15×），但同一个改动把 640×360 的 gaussian-blur 从 1.64× 压到 1.39× ——
一个按像素数的启发式分不开「便宜的点算子」和「昂贵的模糊」，净效果为零，已回滚。
另试过把 Rgba8 点算子表改成 32 位打包读写（一次 load/store 替代四次）：**无收益**（1.15× → 1.14×），同样回滚。
**Rgba16 的短板很集中**：三个点算子（grayscale / sepia / invert）在三种尺寸上都是 0.63–0.67×，
因为 `PointLut` 只对 `Rgba8` 生效，16 位走的是 float 行路径。这是矩阵第一次运行就暴露出来的真问题。

> **2026-11-15 修复**：新增 16 位点算子表（4 × 65536 个 `ushort`，512 KiB），用与 Rgba8 相同的手法构造——
> 拿算子自己的行变换跑每个值、记下结果，因此不存在第二份算术。低于 `Lut16PixelFloor`（16384 像素）不建表。
> 逐通道算子（invert / brightness / gamma / contrast）走这张表；矩阵类算子（sepia / grayscale）不走，
> 三条独立测量确认它们字节未变。Rgba16 整体：**1.53–1.72×（4/7）→ 2.01–2.29×（7/7）**。

> **2026-11-15 修复**：新增 16 位点算子表（4 × 65536 个 `ushort`，512 KiB），用与 Rgba8 相同的手法构造——
> 拿算子自己的行变换跑每个值、记下结果，因此不存在第二份算术。低于 `Lut16PixelFloor`（16384 像素）不建表。
> 逐通道算子（invert / brightness / gamma / contrast）走这张表；矩阵类算子（sepia / grayscale）不走，
> 三条独立测量确认它们字节未变。Rgba16 整体：**1.53–1.72×（4/7）→ 2.01–2.29×（7/7）**。

**8K 暴露的短板（已修，见下）**：Rgba16 在 8K 只有 5/7，落后的两项是 **grayscale 0.67× / sepia 0.68×**——它们是**矩阵类**
算子，不吃逐通道表，走 `Pixels.ReadRowRaw` / `WriteRowRaw` 的 float 行路径，而 **Rgba16 的这两条读写路径是
逐像素标量**（每像素 4 次 `ushort × (1/65535)`、回来再 4 次 `ToUInt16`）。1080p 上看不出来（那两项还是 1.3×），
8K 上 33 MPix 把它放大成 148 ms vs 对手 99 ms。这是**所有 16 位算子的共同瓶颈**，不只是这两个。

> **已修（2026-11-16）**：`ReadRowRaw` / `WriteRowRaw` 的 Rgba16 分支改成八路向量：读 `ushort → widen → int32
> → float → ×1/65535`，写 `×65535 + 0.5 → clamp → trunc`。写入那条必须逐位复现标量的顺序——`Vector256.Max(v, 0)`
> 顺便把 NaN 变成 0，与 x64 上标量 `(ushort)NaN` 的行为一致。**8K Rgba16：1.77×（5/7）→ 2.67×（7/7）**，
> grayscale 148 → **52 ms**、sepia 146 → **52 ms**；两次独立运行 2.6754× / 2.6635×。

## 忘了 `using` 会怎样（`disposecheck`，2026-11-16）

```
dotnet run -c Release --project benchmarks/SimdImaging.Comparison -- disposecheck 7680x4320
```

同一份工作跑 12 次，只差有没有 `Dispose`：

| 尺寸 | 做法 | 分配总量 | 峰值增量 | 强制回收后常驻 | 每轮分配 |
|---|---|---|---|---|---|
| 4K | `using` | 96.2 MB | 97.6 MB | 95.8 MB | **8.0 MB** |
| 4K | **不 Dispose** | **352.3 MB** | 351.5 MB | **0.0 MB** | **29.4 MB** |
| 8K | `using` | 334.1 MB | 335.8 MB | 333.4 MB | **27.8 MB** |
| 8K | **不 Dispose** | **1397.7 MB** | 1372.7 MB | **0.0 MB** | **116.5 MB** |

**结论一：不是泄漏。** 强制回收后常驻是 **0.0 MB**——内存全部被 GC 收回，没有引用链钉住它。

**结论二：池失效。** 每轮分配从 27.8 涨到 116.5 MB（8K，4.2 倍），因为缓冲没还回池，下一轮只能重新租。

**结论三：峰值翻四倍。** 8K 下从 336 MB 涨到 1.37 GB，全部落在 LOH——长驻服务里这既是吞吐问题也是 OOM 风险。

所以 `using` 的必要性不是风格问题，它决定了**池还能不能用**。

### 终结器兜底做到了什么、没做到什么（2026-11-16 加，同日实测）

`WorkingBuffer` 现在有终结器：没被 `Dispose` 的缓冲在 GC 到它时**仍会还给池**。实测（4K，40 轮）：

| | 每轮分配 | 强制回收后常驻 |
|---|---|---|
| `using` | 2.4 MB | 95.8 MB |
| 不 Dispose（有终结器） | **29.6 MB** | **64.0 MB** |
| 不 Dispose（无终结器，改前） | 29.4 MB | **0.0 MB** |

**终结器把「永久失去」变成了「延迟归还」**：常驻从 0 变成 64 MB，说明缓冲确实回到了池里。

**但它救不了这一刻的分配**——29.6 MB/轮几乎没变，因为终结器只在 GC 时运行，赶不上下一轮 rent。

### 池的库存上限：**不随忘记的次数增长**

`ArrayPixelPool` 对超过 4 MiB 的缓冲按「1 MiB 粒度」分组，每组**最多留 2 块**（`MaxPerSize = 2`，
注释写着「两块够一对乒乓」），超出直接丢掉、交给 GC：

```csharp
if (bag is not null && array is not null && bag.Count < MaxPerSize)
    bag.Add(array);
```

所以「库存」的硬上限是**每组两张大缓冲**：

| 尺寸 | 单张 | 池最多持有 | 实测常驻 |
|---|---|---|---|
| 4K | 33.2 MB | **66.4 MB** | 64.0 MB ✓ |
| 8K | 132.7 MB | **265.4 MB** | 254.0 MB ✓ |

**忘了 10 次还是 1000 次，库存都是这两块。** 涨的不是库存，是**过手量**——每轮租一张新的、
旧的等 GC 时才回来，于是分配计数一路累加（这才是 4/12 倍那个数字）。

4 MiB 以下走 `ArrayPool<byte>.Shared`，那里同样有每组上限，由框架保证。

结论：**兜底是为了不让池的库存在长驻进程里永久流失，不是为了让 `using` 变成可选。** 忘了写不会崩、也不会泄漏，但会以 12 倍（4K）到 4 倍（8K）的分配率一直跑下去。


## 融合到底做成了没有（`fusion`，2026-11-16）

```
dotnet run -c Release --project benchmarks/SimdImaging.Comparison -- fusion
```

**判定不看时间，看托管分配与 `IPixelPool.Rent`**：融合的行带窗口只租输出、边读源边算；逐步执行会在每一级
之间落一张中间图。计时用 `Timing.Time`（7 轮交错取中位）。四尺寸 × 六种链形，比值 = 计划 ÷ 逐次（<1 表示融合更快）。

| 链条 | 640×360 | 1080p | 4K | 8K | 8K 分配（计划 / 逐次） |
|---|---|---|---|---|---|
| 点算子 ×1 | 1.47× | 1.40× | 1.48× | 1.41× | **19 KiB / 6 KiB** |
| 点算子 ×3 | 1.70× | 1.15× | 1.31× | 1.25× | **45 KiB / 127 MiB** |
| 点算子 ×5 | 1.55× | 1.03× | 1.10× | **0.99×** | **72 KiB / 381 MiB** |
| 模糊 σ=1 + 2 点 | 1.60× | 1.18× | 1.14× | 1.16× | 4.0 MiB / 127 MiB |
| 模糊 σ=3 + 2 点 | 1.50× | 1.05× | 1.07× | 1.13× | 48 KiB / 144 MiB |
| 模糊 σ=8 + 2 点 | 1.30× | **0.81×** | 1.01× | 1.11× | 52 KiB / 127 MiB |

**结论一：融合成立，且内存优势随链长与尺寸放大。** 五步点算子链在 8K 上：计划 **72 KiB**，逐次 **381 MiB**
——5300 倍。融合省的是「每级一张整图」。

**结论二：融合的代价取决于链长，不是尺寸。** 单点算子在**每一个尺寸**上都慢 **1.4–1.48 倍**，而且这个比值不随
尺寸收敛——它不是固定开销，是**每像素多两次搬进搬出**。一步链只产出一次，这两次搬运没有任何东西可省。

**结论三：链越长、半径越大，融合越划算。** 五步链在 8K 上打平（0.99×），σ=8 的模糊链在 1080p 上就已经反超（0.81×）,
因为逐次那条链要来回搬三遍整图。

**结论四：任意组合也是等价的。** 上面六条链是挑出来的形状，而调用方会按自己的问题组合算子。
`FusedChainPropertyTests` 用固定种子生成 **160 条随机链**（1–7 步，取自 5 个算子：2 个点、2 个邻域、
1 个 `Global`——它会强制切断融合段），在 4 种带高 × 2 种并行度的组合下，把**融合执行与逐步执行**逐字节比对，
全部相等。这是「随意组合行得通」的证据，不是一句声明。

> **可操作的设计规则**：**单步链不要走计划**（纯亏 1.4×，内存也省不下东西）；**≥3 步或带大半径模糊时走计划**，
> 时间持平到反超，内存省 1000–5000 倍。`AllowFusion` 存在的理由就是这个选择权。

## NLM 内层消融（`nlm-ablate`，2026-11-16）

```
dotnet run -c Release --project benchmarks/SimdImaging.Comparison -- nlm-ablate
```

`NonLocalMeans` 是全库最慢算子（1080p S=3 P=1 h=0.1 实测 ~6.7 s）。**先量后改**：复刻 Rgba8 内层循环、
用产品算子逐字节校验复刻件（`SHA 131CC440…`，两次独立运行都为 `True`），一次只把一处换成保持输入存活的
替身（避免常量替身让上游 SSD 被 JIT 死代码消除），`Timing.Time` 交错取中位。两个独立进程各一轮，数字稳定：

| 变体（1080p, S=3, P=1, h=0.1, σ=0） | RUN 1 | RUN 2 | Δ vs full |
|---|---|---|---|
| full（复刻基线） | 6931.9 ms | 6859.4 ms | — |
| `−exp`（`Math.Exp` → `1−e`） | 5571.2 | 5553.0 | **19.0–19.6%** |
| `−ssd-scan`（整段 patch 扫描 → O(1)） | 1479.0 | 1459.8 | **78.7%** |
| `−ssd-sum`（平方乘加 → 差值和） | 6325.9 | 6258.8 | 8.7–8.8% |
| `−mem`（patch 行读 → 热 L1 行） | 6198.8 | 6098.5 | 10.6–11.1% |
| `−all`（exp + 整扫描） | 686.2 | 684.5 | 90.0–90.1% |

四项占比与主因：

| 组件 | 占比 | 对应第二步优化的天花板 |
|---|---|---|
| **patch SSD 整个扫描** | **78.7%** | **滚动 SSD（增量更新 patch 和）** |
| └ 其中平方乘加算术 | 8.7–8.8% | — |
| 平方根 sqrt | **0%（本实现无 sqrt**：`weight=exp(−SSD·normalizer/h²)`） | — |
| 指数 expf | 19.0–19.6% | 权重表（整数 SSD 分档） |
| 内存访问（patch 行读） | 10.6–11.1% | 行带分块 |

**结论一：主因是 patch 扫描本身（78.7%），不是指数（19%）、不是访存（11%）、也没有 sqrt。** 消融第一版
曾把「patch SSD 求和」窄化成「平方乘加」（只有 8.7%），据此会误选权重表；补测整个扫描的 O(1) 替身后排名
才定下来——这正是「先量后否」。三个单替身 Δ 有重叠（扫描里既含访存也含平方），所以它们是**天花板而非划分**；
`Σ(exp + 整扫描)` 与 `−all` 差 ~9% 属该重叠，量级自洽。

**结论二：78.7% 里平方乘加只占 ~9 个百分点，其余是每 tap 的 `Math.Clamp`、`%ringRows`、span 构造与索引**——
所以「滚动 SSD / 增量 patch 和」要消灭的是**整段扫描循环**，而非只替换平方。

**附带发现（不在四项内，但决定绝对时长）**：`NonLocalMeansOps` 调 `RowParallel.For(0, height, …)`，首参传
`width=0`，被 `RowParallel.For` 的 64K 像素门槛判成 **单线程**（`LastWorkerCount=1`）——AGENTS.md 里
「`For` 低于 64K 静默退化、先查 `LastWorkerCount`」正是此坑。算子本已按「每 worker 一条行带、私有 ring」设计，
`For(width, height, …)` 才让它真正并行；`DegreeDoesNotChangeBytes` 已覆盖 worker 数不变字节。这是与内层优化
正交的杠杆，改实现时一并量。

### 结果：滚动 SSD 落地后

`nlm-bench` 是产品算子的端到端秒表（任意尺寸 / 半径，附带输出 SHA 作为字节锚点）：

```
dotnet run -c Release --project benchmarks/SimdImaging.Comparison -- nlm-bench 1920x1080 3 1
```

| 配置 | 改动前 | 改动后（中位） | 变化 | 字节 |
|---|---|---|---|---|
| 1080p S=3 P=1 | 6676 ms | **867 ms** | **7.7×** | 锚点 `131CC44092703366` 匹配 |
| 1080p S=5 P=2 | 19831 ms | **2372 ms** | **8.4×** | 由 `RollingSsdMatchesPerTap_ByteForByte` 覆盖 |
| 4K S=3 P=1 | — | **3010 ms** | — | 同上 |

实现要点：对每个候选偏移先算**列差分行** `col(u)`，patch SSD 变成它的 `(2P+1)` 宽滑动窗口和——
每像素 O(1) 而非 O(P²)。边界行列与 `Rgba32F` 仍走原逐 tap 路径（浮点的 NaN/精确语义不变），
`ForcePerTapSsd` 是**测试钩子**，用于在任意尺寸/格式/半径下与旧算法逐字节比对，不是近似开关。

同一改动里修掉一个与内层无关的杠杆：`RowParallel.For(0, height, …)` 的首参传成了 `width=0`，
被 64K 像素门槛判成单线程——**这个 6.7 s 里有一半是没用上多核**。改为 `For(width, height, …)`。

## 估算器 vs 实测峰值（`memestimate`，2026-11-17）

`MemoryEstimator` 有两处可疑：把整图 scratch 与每线程 scratch **相加**（高估），以及融合段的 halo **不累加**（低估）。
方向相反，只能实测。4K Rgba8，**每个形态一个全新子进程、跑一次**，取 3 次中位数：

| 形态 | 估算 | 实测 | 实测÷估算 |
|---|---|---|---|
| 点链 ×6 | 123.3 MiB | 82.1 MiB | 0.67× |
| 点链 ×6（禁融合） | 123.3 | 82.2 | 0.67× |
| 高斯 ×3（halo 累加场景） | 263.9 | 141.8 | **0.54×** |
| 单 Global 步 | 63.5 | 60.0 | 0.94× |
| 点 ×3 + 高斯 ×2 | 257.3 | 158.2 | 0.61× |

**五档全部高估，没有一档低估。** 最保守的是三连高斯（46%），最准的是单 Global 步（6%）。

**结论：不改公式。** 理论上的两个误差里，**高估那个占绝对主导**；补 halo 累加只会让一个已经保守的估算更保守。
`MaxWorkingBytes` 是安全阀，偏保守的代价是调用方多留内存，偏乐观的代价是超预算——**方向比精度重要**。

**这次测量的第一个版本是错的**：在父进程里预热后再跑，池已经驻留，实测只有 8 KiB——等于「证明」估算高估了三个数量级。
冷启动子进程才是唯一诚实量法。这条写在这里，因为同样的坑踩过一次。

## 点步骤的直写与拷贝（`pointdirect`，2026-11-18）

第三批「Point Direct Write」的前提是**现在多一次拷贝**。读代码确认了：

```csharp
// PlanSteps.Point
using var result = @operator(band);                  // 算子自己租一块 band 缓冲
CopyRows(result.View, 0, destination, ...);          // 再整块拷进目标
```

而字节表核（`AddPointLut`）**直接写 destination**，没有这一步。两条路算术相同（4×256 表），所以差值就是拷贝：

| 路径 | 4K 耗时 | 相对 |
|---|---|---|
| 通用适配器（含拷贝） | 8.42 ms | 1.77× |
| 表核直写 | 4.75 ms | 1.00× |
| **差值** | **3.68 ms** | **占单步 44%** |

1080p 上同样的对照是 1.87 vs 1.32 ms（1.42×，占 29%）——**尺寸越大越贵，因为拷贝是整帧的**。

**已实现，带像素下限。** 表由算子**自己**跑一张 256×1 的探针图得到——没有第二份算术定义，表不可能和它替代的实现漂移。
表是**惰性构建**（`Lazy`，首次执行时建一次），并受 `TablePixelFloor = 128K` 像素限制：低于它走原适配器。

建表成本实测 **27 µs/步**，这是下限存在的理由：

| 尺寸 | 直写节省 | 建表 | 结论 |
|---|---|---|---|
| 4K（8.3 MP） | 1.2–3.7 ms | 27 µs | 走表，省 **17%–47%** |
| 640×480（0.31 MP） | 0.15 ms | 27 µs | 走表，省 **48%** |
| 320×240（0.077 MP） | 0.04 ms | 27 µs | **走回退，0%**——建表会吃掉全部收益 |

**数字波动很大**（4K 五次运行 17%/24%/34%/47%/47%），这台机器不是安静环境。方向一致：走表更快，且越大越明显。

下限不是猜的，和 `Lut16PixelFloor` 是同一个判断：**建表比它省下的还贵时，就不是优化**。

**注意**：融合后的点链**已经走表核直写**，所以这条只影响**单步**点算子——也就是 19 项基准表里的每一项。

## 三个 3×3 算子原本单线程（`one-step`，2026-11-20）

`Morph3x3`、`Convolve3x3` 和 `Sharpen` 的合成循环没有 `RowParallel`，单步链走 `Direct` 时不进分带，于是在一个线程上跑。
`Median3x3` 与 `Gradient` 一直是并行的，所以这不是「所有 3×3 都慢」，而是这几支漏了。

同一把尺子量 `HEAD~1` 与本提交（1080p，算子直调，中位）：

| 算子 | 改前 | 改后 | |
|---|---|---|---|
| Emboss | 90.4 ms | 19.7 ms | 4.6× |
| Erode / Dilate | 88.0 ms | 16.3 ms | 5.4× |
| Sharpen | 100.5 ms | 48.3 ms | 2.1× |
| Median（对照，未改） | 1.10 ms | 0.82 ms | 未受影响 |

**注意 `Direct` 与计划的分工**：单步走 `ImagePipeline.Current()` 的整图快路径，那里算子自己并行；多步走计划，带内
`EnterNested` 让算子串行、由带数提供并行。所以这些算子只在**单步**场景依赖自己的 `RowParallel`。

## 字节不变现在有门禁了（`OperatorGoldenTests`，2026-11-22）

上面每一次「字节完全不变」在此之前都靠临时探针跑一遍，换个会话就没了。现在 22 个算子/参数组合的 SHA-256
落在 `tests/Fixtures/operator-golden.txt`，`dotnet test` 里有一条用例逐项比对——**优化改了输出就不再是「我说没改」，而是构建红**。

要改输出时（只应是缺陷修复），`SIMDIMAGING_WRITE_GOLDEN=1` 跑一次，然后看那个文件的 diff：它就是「哪些算子的字节动了」的完整清单。CI 不设这个变量。

伪证验过：把表里一个十六进制位改掉，用例立刻失败并打印 `算子: 旧哈希 -> 新哈希`。

## 两输入合成为什么建表，门槛取在哪（`lut-cost`，2026-11-21）

`Sharpen` 的合成与 `Glow` 的合成都是「两路取行 → 逐像素 → 写回」，原先每行做三次字节↔浮点往返。
1080p 下 `Sharpen` 的合成曾占 13.7 ms，而它前面的高斯模糊只有 10.6 ms。

改成 64K 二维表（`(源字节, 另一路字节) → 输出字节`）后字节完全不变——表按 `Pixels.ToByte` 的
`v×255+0.5` 截断口径生成，不是 `MathF.Round`。这张表随后与 `HEAD` 的 22 项逐项比对过，全部一致：

| 参数 | 哈希（改前 = 改后） |
|---|---|
| Sharpen 0.6/1 | `02AF5FA05A359F54` |
| Sharpen 1/1.5 | `86CF226C4CB0076C` |
| Sharpen 0.3/2 | `007DCE2A726880EB` |
| Glow 0.6/6/0.8 | `9AEE60F473E6C064` |
| Glow 0.7/2/0.5 | `6F3891EE60D91FFE` |

**但建表本身要钱**，所以有像素下限。`dotnet run -c Release --project benchmarks/SimdImaging.Comparison -- lut-cost 9`：

| 尺寸 | 浮点 | 查表 | 判定 |
|---|---|---|---|
| 64×64 | 0.141 ms | 0.320 ms | 浮点更快 |
| 128×128 | 0.571 ms | 0.222 ms | 查表更快 |
| 512×512 | 1.164 ms | 0.496 ms | 2.4× |
| 1024×1024 | 5.269 ms | 1.342 ms | 3.9× |
| 2048×2048 | 19.78 ms | 5.437 ms | 3.6× |

建表 0.16–0.26 ms。交点 = 建表 ÷ 每像素节省：并行区间约 6 ns/像素 → 约 43K 像素；低于并行闸门时浮点路径每像素贵四倍，
交点降到 4K 附近。**这个跨度比共享机器上一次计时能分辨的还宽**，所以常量不去对交点，直接取
`RowParallel.MinWorkPixels`（64K 像素）——引擎里只留一个「值得付固定成本」的边界。

与既有门槛的关系：`TablePixelFloor = 128K`（1K 项表，建表 27 µs）和 `Lut16PixelFloor = 512K`（65,536 项，
建表 2.3 ms，每次委托调用）是同一判断的不同数值，差别来自**建表成本差 9 倍**，不是口径不同。

**Sharpen 对 ImageSharp（1080p）**：改前 21.8 ms（0.56×），改后 **12.5 ms（1.01×）**，对手 12.6。

## 区域读取的读放大量（M17，2026-11-25）

协议：`TiffFixture` 同款输入——512 宽、RGB8、`RowsPerStrip=32`、确定性高熵图案，经 codec 的 TIFF 编码器写出
（deflate）。用 `Image.ProcessRegion(stream, emptyPlan, rect)` 读 16×16 区域，`CountingStream` 统计从流里真正
读出的字节（`Read` 累计，不看 seek）。

| 图像 | 文件字节 | 区域读字节 | 占文件 |
|---|---|---|---|
| 512×512 | 43 766 | 3 056 | 7.0% |
| 512×2048 | 174 450 | 3 440 | 2.0% |

两行的读量差 12%，来自目录（IFD + 段偏移数组）随条带数增长；**与像素总量无关**。区域本身落在一条 32 行条带内，
所以 3 KB ≈ 条带 49 152 字节的 deflate 后大小 + 目录。整图 `Load` 会把 43.8 KB / 174.5 KB 全部读入托管堆。

复跑：`dotnet test --filter RegionEndToEndTests` 断言 `shortFile < 786 432/8` 且两次读数相差 ≤25%；
上表的绝对值来自同参数的临时探针（未入库）。

## 区域执行的带高阈值（M17，2026-11-25）

同一批像素（512×512，3 步：Brightness → GaussianBlur(1) → Contrast），只改 `BandRows`；9 次取中位。
整图执行同一 512² 图像作基线 **10.09 ms**。

| `BandRows` | 区域执行 |
|---|---|
| 默认（512 宽 → 64） | 36.82 ms（首轮，含预热噪声；显式 64 行 14.79 ms） |
| 64 | 14.79 ms |
| 96 | 14.80 ms |
| 128 | 12.35 ms |
| 192 | **3.05 ms** |
| 256 | **3.93 ms** |
| 512（单带） | **3.84 ms** |

拐点在 128→192：`RowParallel.For` 按 32 行/worker 切分，128 行只够 4 个 worker，且窗口像素数刚过
`MinWorkPixels`。修法是 `SequentialBands`（≥ degree×32 行、≥ 64 K 像素、≤ 4 MiB/窗口）。修正后：
512² 区域 9.7 ms（同像素整图 8.1 ms），2048² 区域 59.6 ms（整图 73.1 ms）。

## `ProcessTo` 的读放大（2026-11-25）

`ProcessTo(stream → stream, Invert)`，`CountingStream` 统计 `Read` 字节。

| 输入 | 文件字节 | 实际读出 | 倍数 |
|---|---|---|---|
| PNG 512×2048 | 57 383 | 122 958 | 2.14× |
| JPEG 512×2048 | 806 229 | 1 616 554 | 2.01× |
| TIFF 512×2048 | 174 450 | 593 688 | 3.40× |

成因是 `ResolveFormat` 的 `ImageDecoder.Open(stream)`：单看它就吃掉了整份文件（JPEG 202 007 → 206 103；
TIFF 71 662 → 147 420；PNG 14 417 → 8 192，`Metadata` 再补到 22 609），随后行读器再读一遍。

**2026-11-25 修复后**（同一批文件，`ProcessOptions` 默认 / `PreserveMetadata = true`）：

| 输入 | 文件字节 | 默认读出 | 默认倍数 | 保留元数据 | 倍数 | `MetadataCarried` |
|---|---|---|---|---|---|---|
| TIFF | 174 450 | 245 510 | **1.41×** | 593 688 | 3.40× | false / true |
| PNG | 57 383 | 61 479 | **1.07×** | 122 958 | 2.14× | false / true |
| JPEG | 806 229 | 810 325 | **1.01×** | 1 616 554 | 2.01× | false / true |

TIFF 的 1.41× 来自 codec 行读器自身的预读（`OpenRowReader` 约 66 KB + 按条带读），不是本库的额外扫描。

## 行流式缩放（M18 第一切片，2026-11-25）

`Image.ResizeTo`（`StreamingResize`）对 `Load → Resize`，同机同进程交替执行：

| 输入 | 流式 | 整图 | 比值 |
|---|---|---|---|
| 7680×4320 → 1920×1080，Bicubic，PNG | 390 ms | 426 ms | **0.92×** |
| 7680×4320 blur+contrast → 缩放 → sharpen | 835 ms | 791 ms | 1.06× |

输出文件逐字节相同。整图那条路的累计分配 131.3 MiB（一张 8K RGBA8 = 126.6 MiB 本身）；流式的第二次调用
只新分配 0.2 MiB（ring/暂存由 `FloatScratch`/`ArrayPool` 复用）。**这不是峰值**：峰值按公式估为
ring `408×1920×16B` ≈ 12.5 MiB + 暂存 `64×30KB` ≈ 2 MiB + 输出带 0.8 MiB ≈ **15 MiB**，
`An8KDownscale_FitsTheDefaultBudget` 证明默认 24 MiB 预算下不拒绝。

等价性：4 尺寸（降/升/恒等/奇数）× 2 深度（Rgba8/Rgba16）× 5 滤波器（Nearest/Bilinear/Bicubic/
Lanczos3/Box）= 40 组，全部与 `Resample.Resize` 逐字节相同；带计划前缀（blur+contrast）的链与
`Load → Apply → Resize` 逐字节相同（含 8K 的 PNG 文件比对）。

注：本机在长时间会话后整体变慢（同一路径 383→485 ms 的波动见过），比值比绝对值稳定，上表复测两轮取值。

## 性能回退门禁：2026-11-25 的四次运行

M16–M18 改过带高规则（顺序出带改 `SequentialBands`）、文件流式的头部探测、以及整条行管线（拉式）。
在 `windows-10.0.19045-x64-16-m16` 基线上连跑四次（同一二进制，间隔数分钟）：

| 次 | 结果 | 最差项 |
|---|---|---|
| 1 | FAIL | `quantize 4K -> 64 (octree)` +30.6%（阈值 30.0%） |
| 2 | PASS | `gainmap resize 1080p->720p` +19.6% |
| 3 | FAIL | `stroke 4K ellipse path (aa, w=6)` +25.9%（阈值 25.0%） |
| 4 | PASS | `chroma 4:2:0 4K` +24.4% |

四次里两次失败、失败项各不相同，且都不在这一轮改过的路径上（`quantize` 是整图 `Global` 步、`stroke` 是绘制）。
结论：这台机器今晚的噪声地板就在阈值附近，**门禁仍然有效但会偶发误报**。M15 的记录里同机 4 小时漂移
1.2–1.8×，与此一致。

**重录尝试与工具缺口**：按「当前树重录一份基线」执行时发现 `BaselineJson.Write` **恒写
`"thresholdPercent": null`**——录出来的基线一条都不设闸，`check-baseline.sh` 还会打印
`PASS ... (0 enforced)`。这正是仓库最反对的「绿的 gate 什么都没验」。处理：

1. 已给 `check-baseline.sh` 加守卫：可比基线存在但一条都没设闸时 **FAIL**，不再假绿。
2. 暂不替换 m16 基线：阈值需要按「五次运行归一化后的偏差 `max(20, ceil(3×S))`」手工推导，仓库里没有录制脚本；
   在噪声地板附近录出来的阈值要么过宽（掩盖回归）要么过窄（继续误报）。
3. 待办：写一个录制脚本（N 次运行 → 归一化中位值 + 阈值），再用它产出 `-m18.json` 替换 `-m16.json`。
