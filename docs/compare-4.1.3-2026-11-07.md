# SimdImaging vs ImageSharp 4.1.3 — 对比结果（2026-11-07）

> **口径**：同进程交替采样，两侧共用同一套热身协议；**参照实现放开并行**（不人为锁单线程）。
> 输入为 Rgba8；稳态判定取各算子多次采样的中位，cold（首次调用）单独记账、**不参与判定**。
> 原始数字：[`benchmarks/.../2026-11-07.sizes2.sizes.md`](../benchmarks/SimdImaging.Comparison/results/2026-11-07.sizes2.sizes.md)、
> [`2026-11-07.min2.cores.md`](../benchmarks/SimdImaging.Comparison/results/2026-11-07.min2.cores.md)。
> 前一天的结果见 [`compare-4.1.3-2026-11-06.md`](compare-4.1.3-2026-11-06.md)，**场景数不同（12 → 17），几何平均不可直接对比**。

## 1. 结论

| 尺寸 | 超越判定（稳态） | 领先项 | cold |
|---|---|---|---|
| 640×360 | **1.3139×** | 12 / 17 | 1.3094× |
| 1280×720 | **1.5085×** | 13 / 17 | 1.3325× |
| 1920×1080 | **1.8068×** | 15 / 17 | 1.7053× |
| 2560×1440 | **1.8318×** | 17 / 17 | 1.7381× |
| 3840×2160 | **1.8535×** | 17 / 17 | 1.8293× |

**分辨率越大越领先，单调上升。** 原因是清楚的：我们的优势来自向量路径与行带并行，
两者都需要足够的像素量才摊得开；640×360 只有 23 万像素，固定开销占比过高，是唯一的弱区（12 / 17）。

**两个独立协议互证**：本表（交错、中位、17 场景）给出 1080p **1.8068×**；
`cores` 模式（子进程隔离、两侧交错 21 轮取最小值）给出 1080p 领先 **1.59–1.72×**。量级与方向一致。

## 3. 核数：两边差不多，不是「靠核多赢」

每侧一支独立子进程测量（`cores` 模式）：

| | SimdImaging | ImageSharp |
|---|---|---|
| 平均用核（1080p） | 8–11 | 6–10 |

**ImageSharp 4.1.3 也并行。** 同核数（本库强制单线程）对比：汇总 **1.1–1.3× 偏慢**，
不是早前一度得出的「每核落后 4 倍」。分项波动 ±40%，**只有汇总值可引用**。

分项里唯一两轮都稳、且同核也领先的是 `gaussian-blur`（直接比 0.58 / 0.60，同核 0.74 / 0.87）。

## 4. 本轮优化记录（**非同时测量，仅量级参考**）

⚠ 下表的「起底」来自不同时间的独立运行，**不是同进程 A/B**，不能当作可审计的倍数。
保留它是为了说明工作量，不是为了宣传。字节正确性由各自的参照测试保证（共 6 个测试文件）。

| 算子 | 起底 | 现在（1080p） | 手段 |
|---|---|---|---|
| median3x3 | 575 ms | 0.8–1.2 ms | 选择网络 → 分支消除 → 字节域 SIMD（16 车道） |
| equalize | 36–45 ms | 1.6 ms | 一趟三通道整数直方图 + 行带并行 |
| oilpaint | 414 ms | 38–44 ms | 行带并行 → 滑动窗口直方图 |
| sobel | 51 ms | 7.2 ms | luma 环缓存 + 去每行分配 + 并行 |
| bokeh | 533 ms | 27–40 ms | 行带并行 → 移位行累加（169 taps） |
| sharpen | 282 ms | 30–32 ms | 同上（`Convolve2D`，81 taps） |
| bilateral | 412 ms | 73–86 ms | 行带并行（剪枝不可行，已论证） |
| clahe | 80 ms | 21–27 ms | 直方图按 tile 行切 + 应用按行带 |
| resize-nearest | 2.17 ms | 0.30 ms | 绕开通用可分重采样，按权重表索引直接搬运 |

**`emboss` 没有变化**（38 → 38 ms）：移位累加每行多三次整行 pass，9 taps 摊不平，
说明该技术有 tap 数门槛（≳25 才划算）。这条已记录，避免以后重复尝试。

## 5. 无法对标的算子

以下算子在 ImageSharp 4.1.3 中**没有对等实现**（部分是编译期确认：该扩展方法不存在），
因此不给倍数，只在实验台做单侧展示：`median` / `sobel` / `sharpen` / `oilpaint` / `bilateral` /
`clahe` / `hue` / `gamma` / `posterize` / `bokeh` / `guided` / `adaptive` / `quantize` 系列。

`brightness` 有同名算子但语义不同（本库加性偏移、参照实现乘性，对拍 PSNR 仅 4.23 dB），
**只展示效果，不给倍数**。

## 6. 复现

```bash
dotnet build benchmarks/SimdImaging.Comparison -c Release

# 单尺寸（默认 1920x1080）
dotnet run -c Release --project benchmarks/SimdImaging.Comparison -- perf 1920x1080

# 五个尺寸 + 翻转标记（推荐；单尺寸结论不算定论）
dotnet run -c Release --project benchmarks/SimdImaging.Comparison -- sizes

# 同条件对比与核数（子进程隔离）
dotnet run -c Release --project benchmarks/SimdImaging.Comparison -- cores 1920x1080
```

⚠ 跑之前**停掉本机其他负载**（例如实验台）。这台机器上实测过：实验台挂着时，
子进程计时整体抬高约 50%，但两侧同向，比值影响较小、绝对值影响很大。

## 7. 已知问题

1. **`resize-nearest` 在 640×360 静默单线程，已修但收益有限。** 根因：Nearest 快路径用的是
   `RowParallel.For`，它有 64 K 像素门槛，而 640×360 → 320×180 的输出只有 57.6 K，于是退到单线程
   （`LastWorkerCount = 1`）。改用 `ForBands` 后 worker 数升到 5.5，**本库绝对耗时 0.1419 → 0.1229 ms
   （−13%）**，输出逐字节不变。

   ⚠ **但比值从 0.22× 变成 1.25× 主要是参照实现数字动了**：同一格参照实现在两次 `perf` 里分别是
   **0.0310 ms 和 0.1542 ms（差 5 倍）**。所以此前的「640×360 输 4.5 倍」本身就不成立——
   它是建立在一个不可复现的 0.031 ms 上的。这一格只能报「本库 0.12 ms、同核数持平」，
   **比值不报**。
2. **`grayscale` / `sepia` 在 720p 掉到 0.83–0.84×**，大图才回到 1.2–1.4×。
3. **分项不可单点引用**：同一算子两次运行的比值可差 40%，只有几何平均稳。
4. `box-blur` / `gaussian-blur` 在 640×360 落后（0.66 / 0.80），到 1080p 才转为领先。
5. **两套协议在小图上分歧很大**，原因是它们回答不同问题：`perf` 每侧连续跑 30 ms 取中位（**吞吐口径**，
   含交替扰动），`cores` 21 轮单次调用取最小（**最小延迟口径**）。640×360 上同一份代码 `perf` 给
   1.47×、`cores` 给 3.4×。对外引用**吞吐用 `perf`，单次延迟用 `cores`**，不能混用。
