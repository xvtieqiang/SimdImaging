## 二、格式与尺寸覆盖：三格式 × 四尺寸

`Rgba8` 19 项、`Rgba16` 7 项、`Rgba32F` 8 项，640×360 / 1080p / 4K / 8K 各跑一遍：

**合并 `ImageChain` 之后重跑的一遍**（`results/2026-11-16.aftermerge.matrix.md`）：

| 尺寸 | Rgba8 | Rgba16 | Rgba32F |
|---|---|---|---|
| 640×360 | 1.71×（14 领先 / 2 持平 / 3 落后） | **2.90×（7/7）** | **8/8** |
| 1920×1080 | **2.27×（18 领先 / 1 持平）** | **2.74×（7/7）** | **8/8** |
| 3840×2160 | **1.96×（19/19）** | **2.73×（7/7）** | **8/8** |
| 7680×4320 | **2.00×（19/19）** | **2.60×（7/7）** | **8/8** |

640×360 的三项落后：`pixelate 0.68×`（真实，已判定不做）、`saturation 0.94×`（持平带边缘）、
`resize-nearest 0.77×`——后者是**已知噪声项**，同一构建的不同轮次在 0.93–2.74 之间摆动，
六轮中位 1.39，单次读数不可引用。

**多尺寸抓到的两个真问题**（单尺寸看不见）：

1. **8K 的 Rgba16 编解码**：grayscale/sepia 在 1080p 是 1.3× 赢的，8K 掉到 0.67×——根因是
   `ReadRowRaw`/`WriteRowRaw` 的 Rgba16 分支逐像素标量。向量化后 8K Rgba16 从 **1.77×（5/7）→ 2.67×（7/7）**。
2. **640×360 的 16 位表门槛**：`invert` 读 0.19×（六轮全落后），因为 65536 项建表成本（2.3 ms）压在小图上。
   门槛从 16384 抬到 524288，同一格 **0.19× → 3.48×**。

## 三、公共 API

### 一条链，写法只有算子

```csharp
using var result = image.Pipe().Brightness(0.05f).Sharpen().Resize(1920, 1080).ToImage();
```

- **halo 由算子自己带**（`PlanOps` 工厂从参数推导），调用方写不出来、也写不错。
- **`PlanSteps` 与字符串版 `Add(name, category, kernel, haloX, haloY)` 已转 `internal`**——公共面只剩 `Add(ImageOp)`。
- **尺寸变化自动切段**：`Resize`/`Crop`/`Rotate90/180`/`Flip*` 由库切开，不是调用方的规则。
- **需要整图的算子照样能进链**（`Vignette`/`CLAHE`/`LocalLaplacian`/`Normalize`/`AdaptiveThreshold`/`Pixelate`），
  当独立一段执行，写法不变。

覆盖率 35 个算子，判定依据见 [`pipeline-coverage.md`](pipeline-coverage.md)。

### 融合的实测代价

| 链 | 640×360 | 1080p | 4K | 8K | 8K 分配（链 / 逐次） |
|---|---|---|---|---|---|
| 点算子 ×1 | 1.47× | 1.40× | 1.48× | 1.41× | 19 KiB / 6 KiB |
| 点算子 ×3 | 1.70× | 1.15× | 1.31× | 1.25× | 45 KiB / 127 MiB |
| 点算子 ×5 | 1.55× | 1.03× | 1.10× | **0.99×** | **72 KiB / 381 MiB** |

**融合是内存优化，不是时间优化**：五步链在 8K 打平、内存省 5300 倍；单步链反而慢 1.4×（没有中间图可省）。

## 四、内存

| 事项 | 结果 |
|---|---|
| 池库存上限 | 每组 2 张大缓冲（4K 66 MiB / 8K 265 MiB），**与忘记释放的次数无关** |
| 忘了 `using` 的代价（8K） | 每轮分配 27.8 → **116.5 MB**，峰值 336 → **1373 MB**，但强制回收后常驻 0（**不是泄漏**） |
| 终结器兜底 | 常驻从 0 → 64 MB（4K 40 轮），说明缓冲**确实回到池里**；但每轮分配不变——回得晚，赶不上下一轮 |

## 五、负结论（都有实测，不是判断）

| 方向 | 结论 | 依据 |
|---|---|---|
| 增量能量更新 | **不做** | 能量只占 `FindSeam` 17%（消融：400.5 → 331.4 ms），天花板 14% |
| chroma 子采样合并 | 无收益 | 读写省 25%，1.5× 目标价更高 |
| KD-tree 选色 | 负收益 | 16384 色仍慢，索引成本压过剪枝 |
| guided 双平面融合 | 无收益 | 227–251 ms vs 单平面 228–232 ms（同机同时段） |
| pixelate 追平 | 不做 | 3.10 vs 2.36 周期/像素，差的 0.74 需字节域 SIMD，只值 0.05 ms |
